Dev & accessibility notes

  • Totals layout (updated to match production): the proposal-level Totals card now uses the same two-row pattern as the live UI — a plain "Subtotal" row and a dark "Total" bar below it. Subtotal mirrors Total here since no proposal-level tax/fee logic is in scope for this ticket; if a future ticket introduces one, Subtotal would diverge from Total at that point.
  • Menu structure (updated to match production): the ⋮ menu now mirrors the live "Squire" package menu exactly — an Actions group (Edit Package, Duplicate Package, Apply Discount) and a Status group (Mark as Recommended, Select Package), with Delete Package separated below. Icons are inline SVG (Feather-style), aria-hidden, so the button's own text is what assistive tech announces.
  • Proposal Total fix (not one of the 86bc33f26 BRs — a related correction): the Proposal Total now stays $0.00 until a package is marked Selected via the Status group, matching the existing single-package-selection model. Selecting a different package deselects the previous one (mutually exclusive) and the total switches to that package's live total, including any applied discount.
  • Select Package semantics: modeled as role="menuitemradio" with aria-checked across the three packages' Select Package items, so assistive tech gets an explicit checked/unchecked state rather than relying on the visual "Selected" pill alone. Open question for PM: clicking "Select Package" on the already-selected package toggles it off in this prototype (returning the total to $0.00) since the label doesn't change to "Deselect" — confirm this matches intended behavior, or if an explicit "Remove Selection" state is preferred.
  • Placement decision: "Apply Discount" lives in the package's existing ⋮ menu next to Edit Package, not as a 4th footer button — it's an occasional, one-per-package action (BR-8), and adding it to the Add Area / Add Multiple Items / Add Item row would raise decision cost (Hick's Law) on a row that's already used repeatedly during build-out. Flagging for confirmation since the ticket left placement open.
  • Keyboard/focus: ⋮ button and menu items are native <button>s, 44px hit area, visible focus ring, aria-haspopup/aria-expanded on the trigger, role="menu"/role="menuitem" on the list. Escape closes the menu and returns focus to the ⋮ button; clicking outside also closes it.
  • Modal: focus moves to the "Discount" field on open, is trapped in the dialog, and returns to the triggering ⋮ button on close. Quick Discount % buttons use aria-pressed rather than color alone to show selection.
  • Disabled state after applying: per BR-8 (flagged in the ticket as a V1 assumption), the menu item disables with a visible sub-label — not just a tooltip — once a package has a discount line, and a native title attribute backs it up for pointer users.
  • State change announcement: applying a discount posts an aria-live="polite" confirmation ("Discount applied to the Squire package") so screen reader users get the same confirmation sighted users get from the new line item appearing.
  • Two-way sync: Quick Discount buttons, the % field, and the $ field all update each other live against the package's subtotal, matching BR-2.
  • Negative line items reuse the existing line-item row pattern (BR-3) — no new component introduced.
